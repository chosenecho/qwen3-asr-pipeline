# qwen3-asr-pipeline 修改方案

状态：第一轮已实现（2026-11-28）。下文保留设计结构；正式行为、验证范围和暂缓项见文末实施记录。

## 1. 目标与范围

保留 Python 3.10+ 标准库、Windows/Linux、Python CLI 与 Pi 扩展单文件交付的约束。优先修复输出覆盖、过期结果复用、异步任务重复提交和恢复完整性问题，然后整理内部职责。

第一轮完成后，用户应能确认：输出对应哪个输入与参数；临时网络错误会继续轮询原任务；恢复操作在覆盖目标前验证整套归档；公共数据库快照有明确的导出字段范围。

已按方案完成代码、回归测试与文档更新。此前验证用的临时探针、实现脚本和静态报告保留在已忽略的 `.archify/`，不作为正式测试或业务代码。

### 2.3 拟新增的数据库内容

`media_items` 新增 4 个可空 TEXT 字段，现有列继续保留：

| 字段 | 保存什么 | 作用 |
| --- | --- | --- |
| `source_fingerprint` | 视频大小与纳秒修改时间等信息的稳定摘要 | 判断原视频是否发生变化 |
| `audio_fingerprint` | 输入版本、音频 preset 和转换规则版本的摘要 | 判断音频是否符合当前提取要求 |
| `asr_fingerprint` | 音频版本、语言、词级时间戳选项及端点身份等摘要 | 判断已有任务/结果是否符合当前转写要求 |
| `asr_phase` | `submitting`、`submission_unknown`、`polling`、`writing` 或空值 | 解释同一 ASR 状态所处的具体步骤 |

增加 `PRAGMA user_version` 驱动的迁移函数，第一版迁移在事务内添加缺失字段。现有数据库没有明确版本号时，先检查实际表结构，再决定迁移动作。

第一轮不新增任务历史表、租约表或数据库依赖。沿用 `asr_attempts` 表示提交尝试数；恢复轮询不增加提交次数。

指纹第一版采用大小与修改时间，避免每次扫描大型视频都完整计算哈希。它属于快速变化检测：内容变化但大小和修改时间都被保持的情形，仍需显式重建。摘要排除密钥和鉴权头；端点身份以规范化 URL 为基础，同地址后端模型更新时使用显式重转。

### 2.4 拟新增的用户命令与参数

| 命令/参数 | 行为 |
| --- | --- |
| `reconcile` 子命令 | 核对数据库、音频、转写文件和结果标记；默认只输出修复计划 |
| `reconcile --apply` | 执行核对结果：重置缺失或过期的阶段、接纳已完整落盘但未落库的结果 |
| `reconcile --group NAME` | 只核对指定组 |
| `transcribe --poll-retries N` | 限定连续临时轮询错误的重试次数，建议默认 3；成功轮询后计数清零 |
| `package/publish --db-profile public\|private` | 明确数据库导出模式；默认 public |

现有 `--overwrite`、`--keep-remote-task`、`--skip-verify` 和 `reset` 继续保留。`--no-sanitize-db` 作为 private 模式的兼容别名；与显式 public 同时使用时报参数冲突。

不新增服务器、后台常驻进程或新的默认网络探测。

### 2.5 拟新增的运行期文件

- 每条转写结果增加一个隐藏的 `.complete.json` 标记，记录输入/请求指纹、产物文件名、大小与摘要。内容不含凭证。
- 提取、转写与打包产生唯一命名的暂存文件；成功提交后清理。
- 发布批次增加 `release_id` 和暂存目录，区分不同代产物。
- 恢复增加操作日志与目标文件备份，记录已替换文件，支持异常后的回滚或继续。
- 数据库迁移前生成本地私有备份；备份保留原有信息，只存本地忽略目录。

这些是运行期数据，不提交到源码仓库。公共转写归档仍以文本、字幕及可选 JSON 为主；本机完成标记不作为跨平台续跑凭证发布。

## 3. 第一阶段：修复命名和结果有效性

### 3.1 输出路径统一生成

新增内部函数 `build_output_paths()`。对 `lecture.part1.mp4` 先得到完整 stem `lecture.part1`，再追加 `.txt`、`.srt`、`.json`；避免对中间路径再次调用 `with_suffix()` 而截掉 `.part1`。

调度前检查目标路径唯一性。`clip.mp4` 和 `clip.mkv` 等即使规则修正后仍会同名的输入，默认报告冲突并跳过冲突项，不让并发任务覆盖。后续如有实际需求，再提供带稳定 ID 的命名模式。

对历史同名覆盖结果，列出受影响条目并通过显式重转修复；已有文件可能已丢失原内容，单靠重命名不足以恢复。

### 3.2 输入变化向下游传播

- 视频指纹变化：音频和 ASR 都回到待处理，清除远端任务关联及旧结果关联。
- 提取 preset 变化：音频和 ASR 都失效。
- 音频重新生成：按新的音频版本重新判断 ASR 有效性。
- 语言、词级时间戳选项或端点变化：转写结果失效。
- 只新增 JSON 输出需求：已有 JSON 缺失时报告产物缺口；若远端已清理且本地没有原始响应，需显式重转。

失效先更新数据库关联，保留旧文件直到新结果成功提交。用户能够看到待重建原因，避免把旧文件误当作当前结果。

### 3.3 结果采用显式提交标记

写入顺序为：生成并验证所有暂存产物 → 替换目标文件 → 最后写完成标记 → 数据库标记 done → 按配置删除远端任务。

多个文件与 SQLite 之间没有共同事务，方案不宣称整套产物一次性原子提交。通过最后写入的标记、文件摘要与 reconcile 补偿中断窗口：标记有效而数据库未完成时补记完成；文件缺失或摘要不符时报告待修复。

Pi 扩展同样使用提交标记判断跳过，避免仅凭非空 txt/srt 就跳过部分写入的结果。

验收：多点文件名保持完整；目标冲突在请求前发现；写任一文件时中断都不会被当作完整新结果；视频变更会触发下游失效。

## 4. 第二阶段：使异步恢复保留正确任务身份

### 4.1 提交与恢复分开

新增内部 `ensure_remote_task()`，供普通处理与预上传共用。复用条件同时检查任务 ID、规范化端点和请求指纹，避免两条路径各维护一套规则。

创建新尝试前，明确清空旧 task ID，持久化当前请求指纹与 `submitting` 阶段；收到新 ID 后立即持久化，再进入 polling。

如果 POST 发生超时、连接中断，或进程在拿到 ID 前退出，远端是否接收请求可能未知。下一次启动将其识别为 `submission_unknown` 并报告，默认不自动再次提交。用户核实后使用现有 reset 重置，或通过显式 overwrite 发起新尝试；命令说明重复计算的可能性。

服务端将来若支持幂等键，再补强提交重试。当前 HTTP 契约不足以承诺严格一次执行。

### 4.2 错误按是否可恢复分类

- 轮询连接失败、超时、HTTP 429/5xx：保留 task ID，有限退避，尊重合理范围内的 Retry-After。
- 连续错误达到上限或本次等待时间耗尽：保留可恢复任务身份，退出码非零，下次继续轮询。
- 401/403：结束本次运行并提示配置问题，保留任务身份供修正后恢复。
- 明确远端失败/取消：记录 failed，下一轮按已有失败重试策略处理。
- 404/任务过期：报告身份失效，要求显式重建，避免无限轮询或静默重复上传。
- 本地写入失败：保留任务，下一次重新取回结果；完成标记和数据库完成前不清理远端任务。

reconcile 核对远端任务需显式操作，默认仅核对本地文件；常规 status、测试和迁移都不唤醒远端 GPU。

### 4.3 入口契约与清理

共同样例覆盖 `result/data/output` 包装、`segments/utterances/sentences/chunks`、词级结果和空结果。Python 与 Pi 对相同样例应产生相同的文本与规范化时间段；字幕回退时长的已有差异在实现时统一并写入样例。

空文本可能代表无语音，需允许“明确成功且无语音”的结果；结构不匹配的响应作为协议错误，避免静默落成成功空文件。

Pi 默认在本地产物成功提交后删除远端已完成任务，并新增与 Python 同义的 `--keep-remote-task` 选项。Pi 的完整跨进程任务恢复放到可选增强。

验收：一次轮询超时后重跑只发 GET；启动新尝试不会保留旧 ID；提交结果未知时不会自动 POST；普通和预上传路径通过相同样例。

## 5. 第三阶段：发布、校验与恢复

### 5.1 严格验证资产集合

默认恢复要求 MANIFEST 与校验表存在，先校验 MANIFEST 摘要，再核对清单列出的所有资产：文件是否齐全、摘要是否匹配、是否存在重复名称或路径异常。

恢复只处理清单声明的归档。目录有额外归档时给出提示并忽略，避免混入旧代分卷；缺少任何声明分卷时，在写目标前终止。

`--skip-verify` 仅跳过摘要校验，仍保留清单集合检查、路径检查和 `filter="data"`。没有 MANIFEST 的旧目录不走默认恢复，文档给出重新打包步骤。旧版 MANIFEST 已有 assets 列表，应提供兼容读取；新版本加入格式版本。

摘要用于发现损坏和资产混代，不作为发布者身份认证。

### 5.2 批次暂存与失败恢复

打包先在新批次目录完成所有归档、清单和摘要，再交付整批结果。旧完整批次保留到新批次提交成功。现有发布函数跟随最终交付目录读取资产。

恢复先完整验证、在临时目录解包，再按日志替换目标；覆盖前备份目标文件。发生异常时按日志回滚，进程崩溃后可识别未完成日志。运行中的数据库在恢复前需要关闭，避免覆盖活动 WAL 状态。

Windows/Linux 下对多个文件和现有目录替换没有统一的全局原子操作，因此验收重点是可检测、可恢复，并要求恢复期间暂停读写目标目录的进程。

新建 GitHub Release 优先使用 draft，资产上传完成后发布；更新已有 Release 上传资产后最后更新清单，并验证目标集合。不自动删除旧资产，恢复端只读取当前清单。已有公开 Release 更新期间仍可能短暂集合不一致，应校验失败后重试，文档说明这一限制。

### 5.3 数据库导出模式

- public：采用独立导出结构和字段白名单，保留分组、媒体标识、相对路径及必要统计；去除绝对路径、服务 URL、task ID、自由文本错误和运行配置。保留后续 VACUUM。
- private：保留完整状态，用于备份；路径仍依赖原机器，Windows/Linux 路径映射不在第一轮承诺中。
- MANIFEST 增加 `schema_version`、`release_id`、`db_profile`、`sanitization_version`，明确快照用途。
- public 快照标注为归档索引，普通转写启动时检测并提示先建立本地状态；提供查询能力，不将它当作已恢复的可运行任务库。

公开归档里的转写正文和相对文件名仍保留原内容，数据库字段脱敏不等于内容匿名化。

验收：缺少分卷、摘要不符、清单缺失时目标目录保持原样；暂存解包失败不覆盖目标；提交中断可通过日志恢复；public 导出对已定义字段白名单逐项验证。

## 6. 第四阶段：在单文件内部整理职责

正确性修复与测试稳定后，将主脚本内部集中成四个 Module：

1. StateDB：迁移、查询和状态变更；所有数据库操作继续受 self._lock 保护。
2. AsrClient：HTTP 请求、协议解析、任务提交/轮询/清理；允许注入 transport 和等待函数供测试使用。
3. TranscriptStore：路径、产物验证、暂存写入和完成标记。
4. 调度逻辑：并发、预上传、watch、停止；调用前述 Interface，不自行重复恢复规则。

上述名称是拟定实现，不要求机械地都做成类。优先减少调用方需要理解的状态与顺序；避免为每个小函数增加一层转发。

同一数据库的同一阶段/组暂按单活动进程使用。线程安全不等于多个 CLI 进程的任务领取安全，README 明确这个运行约束；真正的跨进程领取与租约留到后续有需求时实施。

## 7. 迁移、兼容与实施顺序

1. 把本次临时探针转为正式回归测试，先覆盖已复现问题。
2. 修正命名、冲突检测与产物提交，处理已覆盖结果的识别。
3. 增加数据库迁移和指纹，补上源文件变化的下游失效规则。
4. 统一普通/预上传提交逻辑，加入错误分类和恢复。
5. 增加 reconcile，完善旧库与旧产物处理。
6. 修复发布恢复，增加 public/private 模式。
7. 同步 Pi 契约和清理行为，最后整理主脚本内部职责。

旧库迁移先备份再加列。对于历史 done 条目，缺少历史指纹意味着旧结果是否匹配当前输入尚未验证。保留历史产物与状态，在首次扫描时记录这一事实；reconcile 显示为“历史结果待确认”，显式采纳后建立基线，或重建生成新结果。默认扫描不触发整库重算，也不把现有文件自动当作已验证新结果。

历史 running/queued 任务可按旧端点和 ID 尝试恢复，但应标注请求参数未验证，禁止把新参数直接视为该任务的原始参数。

旧完成标记不存在时，Python 依赖旧库状态并报告未验证，Pi 报告旧产物并要求显式覆盖或采纳；采纳只能建立当前基线，不能证明历史输入一致。

迁移回滚使用对应版本的数据库备份；代码回滚与数据库回滚要配套。保留旧私有备份，避免依赖公开快照做版本回退。

## 8. 验证与完成标准

建议实施后的本地验证命令：

```bash
python -m unittest discover -s tests -v
python -m py_compile asr_pipeline.py scripts/release_artifacts.py
python asr_pipeline.py endpoints
python asr_pipeline.py --db /path/to/throwaway.db status
```

自动测试只使用临时目录、临时数据库和模拟网络；最后一条命令在 Windows 使用 Windows 临时路径。端点列举不带 --check。真实音频与远端联调另做显式验证，并分别在 Windows Python 3.12 和目标 Ubuntu Python 3.10.12 环境执行。启动时检查 tarfile data filter 能力，保留显式路径校验和 data filter。

Python 与 Pi 测试自动读取契约样例。实施时采用已有 Node 24 的内置 TypeScript 类型擦除和 `node --test tests/test_pi_contract.mjs`，无需 npm 依赖，自动验证 Pi 运行行为；完整 `tsc` 类型检查仍需 Pi 开发依赖环境。

交付完成应同时满足：已复现问题有对应测试；旧库迁移幂等；每条状态变更可解释；正常重跑不重复上传可恢复任务；本地失败保留远端结果；发布恢复在验证前不修改目标；文档与两套入口的实际行为一致。
